# 代码审核数字员工 — 配置说明

本文说明如何登记项目、绑定规范、跑 CLI / 配置页，以及报告落在哪里。

---

## 1. 核心原则

- **一个项目一条登记**：在 `projects.yaml` 里用唯一 `id` 区分。
- **规范按项目、按语言绑定**：`standards.php` / `standards.python` 写**该业务仓里的 `.md` 绝对路径**。
- **某语言列表为空 `[]`**：该语言**不做命名检查**（语法检查仍会做）。
- **绝不会串项目**：审核时只读当前 `--project`（或网页所选项目）绑定的规范。

---

## 2. 文件一览

| 路径 | 用途 |
|------|------|
| `projects.yaml` | 已登记项目（仓库、规范、命名风格、默认分支） |
| `.env` | Kimi / Moonshot API（**勿提交 git**） |
| `.env.example` | 环境变量模板 |
| `standards/python/`、`standards/php/` | 全局兜底目录；**有 `--project` 时不用** |
| `reports/{项目id}/{日期}/` | 审核报告输出 |
| `hooks/` | 本仓库 pre-commit；业务仓请用 CI 调 `scripts/ci_gate.sh` |
| `docs/企业落地.md` | 企业初筛落地、门禁级别、验收清单 |
| `scripts/self_check.sh` | 黄金用例 |
| `scripts/ci_gate.sh` | 业务仓 CI 门禁入口 |

## 3. 新增一个项目

编辑仓库根目录的 `projects.yaml`，在 `projects:` 下追加一段：

```yaml
projects:
  # —— 已有项目保持不动 ——

  my-new-app:                          # ← 项目 id（CLI / 网页用这个）
    display_name: 我的新项目           # ← 页面上显示的名字
    repo: /绝对路径/到/业务仓库
    standards:
      php:
        - /绝对路径/到/业务仓库/docs/php-coding-standards.md
      python: []                       # 没有 Python 规范就空着
    php_method_style: snake_case       # snake_case | camelCase
    php_variable_style: either         # snake_case | camelCase | either
    default_branch: main               # 配置页默认选中的分支
```

### 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| 顶层 key（如 `my-new-app`） | 是 | 项目 id，唯一；`--project my-new-app` |
| `display_name` | 是 | 人类可读名称 |
| `repo` | 是 | 被审 git 仓库的绝对路径 |
| `standards.php` | 否 | PHP 规范 `.md` 路径列表；`[]` = 跳过 PHP 命名 |
| `standards.python` | 否 | Python 规范 `.md` 路径列表；`[]` = 跳过 Python 命名 |
| `php_method_style` | 否 | 默认 `camelCase`；GF 类项目常用 `snake_case` |
| `php_variable_style` | 否 | 默认 `camelCase`；`either` 表示变量风格不硬卡 |
| `default_branch` | 否 | 网页下拉默认分支 |

### 规范文件放哪？

- **推荐**：留在业务仓，例如 `docs/coding-standards-gf.md`。
- CodeReview 只存**路径指针**，不复制内容，避免两份过期。
- 路径必须本机可读；文件不存在时报告里会提示 Missing。

### 兼容旧写法

若仍写成：

```yaml
standards:
  - /path/to/one.md
```

会自动当成 **仅 PHP** 规范（`python: []`）。新项目请用 `php` / `python` 分开写。

## 4. 环境变量（`.env`）

复制 `.env.example` 为 `.env` 后填写：

```bash
MOONSHOT_API_KEY=sk-xxxx
MOONSHOT_BASE_URL=https://api.moonshot.cn/v1
MOONSHOT_MODEL=moonshot-v1-8k
```

| 变量 | 说明 |
|------|------|
| `MOONSHOT_API_KEY` | Kimi / Moonshot Key |
| `MOONSHOT_BASE_URL` | 国内常用 `https://api.moonshot.cn/v1` |
| `MOONSHOT_MODEL` | 模型名，按控制台可用列表填写 |

没有 Key 时：规则引擎（语法 / 命名）仍会跑，LLM 补充步骤会跳过或记一条警告。

## 5. 怎么跑审核

### 5.1 命令行（推荐带项目 id）

```bash
cd /Users/wumm/学习/@Agent/CodeReview
source .venv/bin/activate

# 列出已登记项目
python -m code_review_agent projects

# 审某项目某分支「最近一次提交」
python -m code_review_agent review \
  --project fm-app \
  --last-commit \
  --branch app3.2.4_a6_0615
```

| 参数 | 含义 |
|------|------|
| `--project` / `-p` | `projects.yaml` 里的 id；自动带上仓库与规范 |
| `--last-commit` | 只审该分支最新一笔（必须同时给 `--branch`） |
| `--branch` / `-b` | 分支名 |
| `--base` / `--head` | 不用 last-commit 时，可自行指定对比两端 |
| `--repo` | 一般可省略；有 `--project` 时用登记路径 |

### 5.2 配置页

```bash
code-review-web
# 浏览器打开 http://127.0.0.1:8765
```

操作：选项目 → 选分支 →「最近一次提交」或「相对 base」→ **生成报告** → 页面预览；下方可点历史报告。

改完 `projects.yaml` 后刷新页面即可（接口会重新加载登记表）。若刚大改过代码仍白页，重启一次 `code-review-web`。

**网页审核**：需手动选择
- **分支（待合并）**：功能分支
- **合并分支（目标）**：主分支 / 要合进去的分支  

审的是两者三点 diff（`合并分支...待合并分支`）整段差距，不会默认选中分支。

**性能规则（仅新增行）**

| 级别 | 颜色 | 类别 | 示例 |
|------|------|------|------|
| 致命 | 深红 | SYNTAX | 语法错误、括号不匹配等影响运行 |
| 警告 | 黄 | NAMING / SLOW_CODE 等 | 命名不规范、嵌套循环等 |
| 警告 | 淡红 | SLOW_SQL | SELECT *、LIKE '%x'、循环查库、无 WHERE 的 DELETE 等 |

## 6. 报告在哪

```text
reports/
  {项目id}/
    {YYYY-MM-DD}/
      {分支}_{commit短哈希}_{时分秒}.md
```

例：`reports/fm-app/2026-07-25/app3.2.4_a6_0615_01c59994_142046.md`

报告内含：项目 id、仓库、分支、结论、致命/警告、规范来源说明。

退出码：有致命错误为 `1`，否则 `0`。

---

## 7. 检查清单（加项目时）

- [ ] `projects.yaml` 里 id 不重复  
- [ ] `repo` 是真实 git 仓库，本机能 `git` 访问  
- [ ] PHP / Python 规范路径各自填对，或明确写成 `[]`  
- [ ] `php_method_style` 与业务规范一致（如 GF 用 `snake_case`）  
- [ ] `default_branch` 在仓库里存在  
- [ ] `.env` 已配置（若要用 LLM 补充）  
- [ ] 用 `python -m code_review_agent projects` 能看到新项目  
- [ ] 跑一次 `--last-commit` 或网页生成，确认报告进了 `reports/{id}/日期/`
